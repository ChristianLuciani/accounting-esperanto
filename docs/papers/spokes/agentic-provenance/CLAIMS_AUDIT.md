## (c) Proposed corrections

No MISMATCH findings were found — every code-checkable claim in the paper is accurate against the committed artifacts as of this worktree's HEAD. The following are wording-precision (IMPRECISE) suggestions only; they do not require re-running any script.

### IMPRECISE #1 — "same dataset" framing around the 441 vs. 366 entry counts

**Where:** L270–272 ("The audit runs on the same synthetic dataset as the project's published consolidation validation (imported, not duplicated), so no numbers are constructed for this paper.") and the Table 1 caption (L313–315, "consistent with the published run's 97.3% deterministic resolution rate").

**Issue (not a mismatch, but worth tightening):** `research/experiments/consolidation_v2/results.json` reports `"total_entries": 366`, while `research/experiments/roundtrip_audit/results.json` reports `"entries_in": 441`. The difference is exactly 75 (one row per entity) and is fully explained by `scripts/mass_consolidation_v2.py`'s `add_equity_plug()` (L250–271): plug/balancing lines are POSTED to the ledger but deliberately EXCLUDED from `total_entries` for coverage-statistic purposes ("counting 75 trivially-resolving plugs would pad the deterministic-coverage headline" — comment at L260–261), whereas `scripts/roundtrip_audit.py`'s `_entities_to_tbs()` (L54–61) deliberately keeps plug rows as ordinary rows because its question is conservation/reconstruction, not coverage. Both counts are internally correct for what they measure; a careful reader could still misread "same dataset" as implying the two scripts should report the same entry count.

**Old wording (L270–272):**
> The audit runs on the *same* synthetic dataset as the project's published consolidation validation (imported, not duplicated), so no numbers are constructed for this paper.

**Proposed new wording:**
> The audit runs on the *same* synthetic dataset as the project's published consolidation validation (imported, not duplicated) — no rows are constructed for this paper. The two scripts count "entries" for different purposes and therefore report different totals: the coverage script (\pathtt{mass\_consolidation\_v2.py}) excludes the per-entity balancing (equity-plug) line from its 366-entry coverage denominator, deliberately, so that trivially-resolving plugs cannot pad the deterministic-coverage percentage; the round-trip audit posts those same plug lines as ordinary ledger rows because its question is conservation and reconstruction, not coverage, yielding $441 = 366 + 75$ (one plug per entity). Both figures are correct for what they measure.

### IMPRECISE #2 — "consistent with" phrasing for the 4-escalation match

**Where:** Table 1 caption, L313–315.

**Issue:** The claim that "the four escalated entries are exactly the entries the resolver declines to map deterministically — consistent with the published run's 97.3% deterministic resolution rate" is true at the *count* level (`escalated_entries: 4` in both `results.json` files) and this audit additionally confirmed both scripts share the exact same deterministic `resolve_with_rule()` function and the exact same `build_entities`/`add_equity_plug` dataset generator, so identity (not just count-matching) of the 4 escalated rows across both runs is the expected consequence of determinism. However, this audit did not diff the actual escalated row identities (subsidiary/code/name) between the two `results.json` artifacts — `consolidation_v2/results.json` does not appear to list its escalated rows by identity in a way this audit inspected line-by-line, only the count.

**Old wording:**
> The four escalated entries are exactly the entries the resolver declines to map deterministically — consistent with the published run's 97.3% deterministic resolution rate.

**Proposed new wording:**
> The four escalated entries are exactly the entries the resolver declines to map deterministically. The escalation count matches the published $97.3\%$ deterministic-resolution run entry-for-entry in aggregate (\texttt{escalated\_entries: 4} in both artifacts) and, because both scripts drive the identical deterministic resolver over the identical generated dataset, the two counts are expected to name the same four underlying rows.
